<Section title="모드별 비용 구조와 전환의 기준" id="tradeoffs">

앞선 측정에서 polling 과 interrupt 어느 한쪽도 모든 상황에서 최적이 아니라는 결론이 나왔다. 이 절에서는 그 관찰을 SQPOLL · IOPOLL · 둘의 조합 · 둘 다 끄기까지 네 가지 모드 전체로 확장한다. 각 모드가 어떤 비용을 지불하고 어떤 비용을 회피하는지를 분해해 어떤 상황에서 유리하고 어떤 상황에서 무너지는지 정리한다. 마지막으로 동적 전환을 만든다고 결심했을 때 *무엇을 신호로 보고 판단할 것인가*를 고찰한다.

## IO 한 건의 비용 구조

io_uring 으로 IO 한 건을 처리하려면 크게 두 단계가 필요하다. 앱이 SQ 링에 요청을 올리면 커널이 디바이스 큐에 전달하는 *제출 단계*가 첫 번째이고, 디바이스가 IO 를 끝내고 그 결과가 CQ 링에 도착해 앱이 가져가는 *완료 단계*가 두 번째다.

<CodeBlock language="plaintext" filename="io-path.txt">
{`앱 ──[A 작성]──> SQ ring ──[B 제출]──> block layer ──> 디바이스
                                                          │
                                                       [C] 디바이스 시간
                                                          │
앱 <──[F 읽기]── CQ ring <──[D 통지]──── block layer <────┘`}
</CodeBlock>

각 구간이 비용을 가진다. A · F 는 단순 메모리 쓰기/읽기라 거의 공짜다. C 는 디바이스가 결정하는 값이라 우리가 손댈 수 없다. 우리가 통제할 수 있는 것은 *B 의 제출 경로*와 *D 의 완료 통지 경로* 두 곳이다.

기본 경로에서는 B 가 `io_uring_enter` syscall 한 번이고, D 가 디바이스 인터럽트다. 두 비용 모두 IO 한 건마다 한 번씩 발생하지만 *분할 상환의 양상이 다르다*. 제출 syscall 은 한 번에 N 개의 SQE 를 함께 보낼 수 있어 *batch 로 분할 상환된다*. 백만 IOPS 워크로드도 batch 크기를 1000 으로 잡으면 syscall 은 초당 천 번뿐이다.

반면 완료 인터럽트는 IO 한 건당 한 번씩 발생한다. softirq 단계에서 어느 정도 묶이긴 하지만 본질적으로 batch 가 어렵다. 그래서 *고 IOPS 환경에서 인터럽트 비용이 syscall 비용보다 더 큰 병목*이 되는 경우가 많다.

이 비대칭이 io_uring 의 모든 polling 옵션을 이해하는 출발점이다. 제출 측 비용은 SQPOLL 이라는 도구로 제거할 수 있고, 완료 측 비용은 IOPOLL 이라는 도구로 제거할 수 있다. 그리고 *두 결정은 서로 독립적*이다. 그래서 네 가지 조합이 나온다.

## 네 가지 모드와 비용 프로파일

### 기본 (Nothing)

제출은 syscall, 완료는 인터럽트. 표준 경로다.

지불하는 비용은 IO 한 건마다 발생하는 syscall 한 번과 인터럽트 한 번이다. syscall 은 batch 로 분할 상환되지만 인터럽트는 그렇지 못해 IOPS 가 올라갈수록 인터럽트 처리에 코어가 잠식된다. NUMA 머신에서 IRQ 가 다른 socket 으로 routing 되면 cache miss 와 IPI 비용이 추가로 붙는다.

회피하는 비용은 *추가 코어 점유 0* 이다. 디바이스 종속성도 없다. 어떤 storage 든 작동한다.

유리한 환경은 두 가지다. 첫째는 *느린 디바이스* — HDD 처럼 ms 단위로 느리면 OS 의 μs 단위 오버헤드는 비례적으로 무시된다. 둘째는 *저~중 IOPS 의 다중 워크로드 환경* — 코어를 점유하지 않는 모드가 가장 잘 공존한다. 절전 측면에서도 가장 우수해서 idle 동안 코어가 저전력 상태로 들어갈 수 있다.

불리한 환경은 *빠른 NVMe + 고 IOPS* 다. 인터럽트가 코어를 잠식해 처리량이 천장을 친다.

### IOPOLL only

제출은 그대로 syscall, 완료는 *사용자 스레드가 CQ 를 직접 polling* 한다. 디바이스가 인터럽트를 발생시키지 않고 NVMe poll queue 에 결과를 깔면 사용자 스레드가 spin 으로 가져간다.

요구사항이 있다. NVMe 의 `nvme.poll_queues` 가 0 이 아니어야 하고 (`/etc/modprobe.d/nvme.conf`), `O_DIRECT` 가 강제되며, block layer 가 polled IO 를 지원해야 한다.

지불하는 비용은 *사용자 스레드가 polling 하는 동안의 CPU 시간*이다. 이 비용은 디바이스 wait time 에 비례한다. 50μs NVMe 에서 100k IOPS 로 polling 하면 코어 5 개 분량의 CPU 가 polling 자체에 들어간다. 디바이스가 빨라지면 비용도 자동으로 줄어든다.

회피하는 비용은 인터럽트 mode-switch, softirq 스케줄링, 깨어나는 데 걸리는 wake latency 다. *jitter 가 매우 낮아진다*. NUMA cross-socket 에서 IRQ routing 비용도 같이 사라진다.

유리한 환경은 *빠른 NVMe + 단일 IO latency 가 결정적인 워크로드*다. DB 의 random point lookup, 실시간 트레이딩, AI 추론의 캐시 fetch 같은 경우다. CPU 에 여유가 있어 spin 코어를 헌납해도 될 때 가장 효과적이다.

불리한 환경은 *느린 디바이스*다. 폴링하는 시간만큼 코어를 통째로 점유하므로 ms 단위 디바이스에서 IOPOLL 은 자살에 가깝다.

### SQPOLL only

제출은 *커널 측 kthread* 가 자동으로 한다. 사용자는 SQ 링에 entry 만 깔면 syscall 없이 IO 가 디바이스로 내려간다. 완료는 인터럽트로 들어온다.

요구사항으로 *registered files* 가 강제된다. kthread 가 사용자의 fd table 에 직접 접근할 수 없기 때문에 미리 등록된 fd 만 다룰 수 있다.

지불하는 비용은 *코어 1 개의 상시 점유*다. 트래픽이 0 이어도 NEED_WAKEUP 동작을 활용하지 않으면 100% busy-loop 다. 인터럽트는 그대로 남아있고, kthread 와 사용자 스레드 사이의 cache coherency 비용이 추가로 붙는다.

회피하는 비용은 *제출 syscall 자체*다. 이게 가장 큰 이득이다. 제출 빈도가 높은 워크로드일수록 amortize 가 잘 된다.

유리한 환경은 *높은 제출 rate 와 풍부한 코어*다. 데이터센터의 스토리지 노드, ML training 의 data loader, 작은 IO 를 폭격형으로 쏟아내는 워크로드가 여기 해당한다. 사용자 스레드가 IO 외에도 컴퓨테이션을 한다면 syscall 에서 풀려난 시간을 그쪽에 쓸 수 있어 가치가 더 커진다.

불리한 환경은 두 가지다. 첫째는 *코어가 적은 시스템* — 4 코어에서 SQPOLL 한 코어 헌납은 25% 다. 둘째이자 더 중요한 것은 *다른 워크로드와 코어를 공유하는 환경*이다. SQPOLL kthread 가 자기 코어를 다른 process 에 빼앗기면 SQ 를 polling 할 수 없어 *IO 제출 자체가 멈춘다*. 처리량이 cliff 처럼 떨어진다. 앞 절에서 stress-ng 100% 부하 구간에서 SQPOLL 처리량이 idle 의 42% 까지 떨어진 것이 정확히 이 현상이다.

### IOPOLL + SQPOLL

제출은 kthread, 완료는 사용자 스레드의 polling. 모든 OS 개입이 사라진다.

지불하는 비용은 *코어 2 개의 상시 점유*다. SQPOLL kthread 와 사용자 reap 스레드가 둘 다 busy-loop 한다. NVMe poll queue · registered files 모두 필요하다.

회피하는 비용은 syscall 과 인터럽트 *둘 다*다. 이론상 OS 오버헤드 0 에 가깝다.

유리한 환경은 매우 좁다. *수백만 IOPS · 마이크로초 이하 latency · 32+ 코어의 dedicated 머신* 정도가 합리적인 영역이다. DPDK 스타일 storage 노드, HFT, 일부 HPC 워크로드, 그리고 "io_uring 으로 X 백만 IOPS 가능"이라는 벤치마크 시연이 여기에 해당한다.

불리한 환경은 *위 조건이 안 맞는 거의 모든 환경*이다. 두 코어 헌납을 정당화하지 못하는 워크로드라면 SQPOLL 만 쓰거나 IOPOLL 만 쓰는 것이 거의 항상 더 효율적이다.

## 상황별 매트릭스

세 축을 동시에 보면 어떤 모드가 정답인지 명확해진다. IOPS, 코어 자원의 여유, 디바이스 속도다. 디바이스 속도는 NVMe (10–100μs) 로 고정한다고 가정하면 나머지 두 축으로 다음 표가 만들어진다.

| | 저 IOPS (~1k) | 중 IOPS (10k–100k) | 고 IOPS (500k+) |
|---|---|---|---|
| **CPU 여유** (격리) | Nothing | IOPOLL | SQPOLL 또는 둘 다 |
| **CPU 부분 경합** | Nothing | Nothing | Nothing 또는 adaptive |
| **CPU 강한 경합** | Nothing | Nothing | Nothing 만 |

빈 칸이 없다. 어느 한 칸의 정답이 옆 칸에서는 차선이거나 자살이다. 그리고 *워크로드는 시간에 따라 칸을 옮겨다닌다*. 백업 시간엔 IOPS 가 폭주하고, 새벽엔 idle 이며, 오후엔 다른 서비스가 갑자기 코어를 가져간다.

<Callout kind="note">
이 매트릭스는 NVMe 기준이라 IOPOLL 이 고려된다. SATA SSD 나 더 느린 디바이스라면 IOPOLL 칸은 모두 사라지고 Nothing vs SQPOLL 의 두 축만 남는다. 그래서 study 의 패치된 fio 에서도 우선 SQPOLL 과 Nothing 의 두 모드 사이의 전환만 다룬다.
</Callout>

## 단일 모드의 한계

위 매트릭스의 모든 칸을 한 번에 만족하는 단일 모드는 존재하지 않는다. 각 모드는 *자기에게 유리한 가정 위에 서 있고, 그 가정이 깨지면 무너진다*. SQPOLL 은 자기 코어를 보장받을 때 가장 빠르지만 코어를 빼앗기면 cliff 처럼 떨어진다. IOPOLL 은 디바이스가 빠를 때 효율적이지만 느려지면 polling 비용이 폭발한다. 기본 모드는 robust 하지만 고 IOPS 에서 인터럽트가 코어를 잠식한다.

이게 *한 가지 모드를 골라 평생 쓰는 것이 적절치 않은 이유*다. 환경이 변하지 않는 워크로드라면 정답을 한 번만 고르면 되지만, 현실의 시스템은 시간대마다 다른 칸에 있다. 운영자가 매번 모드를 바꿔줄 수도 없다.

남은 길은 *시스템 상태를 관찰해 모드를 자동으로 고르게 하는 것*이다. 즉 adaptive 정책이다.

## 전환의 기준점에 대한 고찰

adaptive 정책을 짜겠다고 결심하는 순간 즉시 다음 질문이 따라온다. *무엇을 신호로 보고 결정할 것인가*. 후보가 여럿이고 각각이 측정 비용 · 노이즈 · 반응성의 trade-off 를 가진다.

### 후보 신호들

가장 직관적인 후보는 *시스템 CPU 사용률*이다. `/proc/stat` 의 첫 줄을 두 시점에 읽어 idle 비율의 차이를 계산한다. 측정 비용이 낮고 의미가 명확하다. 단점은 "시스템 전체 평균"이라는 점이다 — 4 코어 중 2 코어가 100% busy 여도 평균은 50% 다. 자기 자신이 묶인 코어에 집중된 경합을 놓친다.

두 번째 후보는 *in-flight QD* 다. polling 의 가치는 동시에 처리되는 IO 가 많을수록 amortize 되므로 QD 가 낮으면 polling 자체의 가치가 떨어진다. 측정은 자기 io_u 카운터를 읽으면 끝이라 가장 가볍다. 단점은 instantaneous 라 노이지하고 burst 워크로드를 잘 잡지 못한다는 점이다.

세 번째 후보는 *latency* 자체다. 평균 또는 p99 가 갑자기 늘어나면 polling 이 망해가고 있다는 가장 직접적 증거다. 의미는 가장 명확하지만 *반응이 늦다* — latency 가 보일 때면 이미 처리량이 떨어진 뒤다. 측정에 IO 를 누적해야 해서 짧은 윈도우에서는 노이즈도 크다.

네 번째 후보는 *SQPOLL kthread 의 CPU 점유율*이다. polling 이 자기 코어를 빼앗기는지 *직접* 측정한다. 가장 specific 한 신호지만 측정 경로가 까다롭다. kthread 의 PID 를 추적하고 `/proc/<pid>/stat` 을 따로 읽어야 하며, kthread 자체가 마이그레이션될 수 있어 정확히 추적하기 어렵다.

다섯 번째는 *디바이스 측 신호*다. NVMe 의 도어벨–완료 latency 같은 driver-level metric 을 보면 더 이른 시점에 polling 효율을 추정할 수 있다. 그러나 일반 user-space 에서 접근 가능한 metric 이 아니라 실용적이지 않다.

### 좋은 신호의 조건

위 후보들 중 어느 것을 고르든 다음 네 가지를 만족해야 한다.

*측정이 가벼워야 한다.* 신호 측정 자체가 polling 의 비용에 더해지면 정책의 가치가 깎인다. /proc/stat 한 줄 읽기는 가볍지만, 매 IO 마다 latency 분포를 갱신하는 것은 비싸다.

*반응이 빨라야 한다.* burst 워크로드에서 신호를 본 시점에 이미 burst 가 끝나 있으면 의미가 없다. 1 분 평균 load average 가 이런 이유로 부적합하다.

*노이즈에 견뎌야 한다.* 출렁이는 신호는 cooldown 이 막아주더라도 결국 진동을 유발한다. instantaneous 측정값보다는 짧은 sliding window 평균이 안전하다.

*인과관계가 있어야 한다.* 신호와 결과가 우연히 상관된 정도라면 정책은 환경 변화에 망가진다. 예를 들어 "초당 page fault 수"는 CPU 경합과 상관될 수 있지만 polling 비용과의 인과관계가 약해 신뢰할 수 없다.

### 이 study 에서 선택한 두 신호

이번 study 의 패치된 fio 는 위 후보 중 *시스템 CPU 사용률*과 *in-flight QD* 둘을 함께 본다. 두 축으로 나누는 이유는 polling 의 비용 구조 자체가 두 축에 걸쳐 있기 때문이다. polling 의 *비용*은 코어 점유에서 오므로 CPU 경합이 첫 번째 신호로 적합하고, polling 의 *가치*는 동시 처리되는 IO 수에 비례하므로 QD 가 두 번째 신호로 적합하다.

<CodeBlock language="plaintext" filename="adaptive-rule.txt">
{`if mode == polling and cpu_pct >= cpu_hi:
    switch to interrupt
    # polling 비용이 너무 비싸짐. 코어 양보.

elif mode == interrupt and cpu_pct <= cpu_lo and qd >= qd_lo:
    switch to polling
    # CPU 여유 회복 + 충분한 병렬성. polling 가치 회복.

else:
    keep current mode
    # hysteresis 영역. 진동 방지.`}
</CodeBlock>

판정 규칙은 단순하다. CPU 사용률이 임계 이상이면 polling 비용이 너무 비싸진 것이므로 interrupt 로 떨어진다. CPU 가 한가하면서 QD 가 임계 이상이면 polling 의 가치가 회복된 것이므로 polling 으로 돌아온다. 두 조건이 겹치는 영역, 즉 CPU 도 한가하지 않고 QD 도 작지 않은 *hysteresis 구간*에서는 *현재 모드를 유지한다*. 진동을 막는 핵심 장치다.

기본값은 `cpu_hi=70`, `cpu_lo=cpu_hi-10=60`, `qd_lo=8`, `cooldown_ms=500` 이다. cooldown 은 한 번 전환한 뒤 최소 500ms 동안은 어떤 신호가 와도 다시 전환하지 않게 한다. 측정 노이즈로 인한 진동을 막는 두 번째 안전망이다.

### 한계와 개선 방향

이 선택에는 분명한 한계가 있다. /proc/stat 은 시스템 전체 평균을 보므로 fio 가 사용하는 코어에 집중된 경합은 신호가 약해진다. 실제로 패치된 fio 를 4 코어 중 2 코어에 묶고 stress-ng 도 같은 2 코어에 묶었을 때, 그 2 코어가 100% 가 되어도 시스템 평균은 50% 에 머물러 임계를 못 넘긴다. 이 한계를 깨려면 *fio 자신이 묶인 CPU 만* 골라서 jiffy delta 를 합산해야 한다. 즉 `sched_getaffinity` 로 affinity mask 를 얻고 그 mask 의 CPU 만 합산하는 변형이다.

QD 신호도 instantaneous 값이라 노이지하다. 짧은 burst 동안 QD 가 잠시 낮아지면 정책이 polling 을 떠나게 만들 수 있다. EWMA 같은 smoothing 을 추가하면 안정성이 올라가지만 동시에 반응이 느려진다. 빠르고 안정적인 두 속성을 동시에 가지는 신호는 없다.

근본적으로 *어떤 단일 신호도 완벽하지 않다*. 정책 설계는 신호의 의미와 한계를 이해한 다음 보수적으로 임계를 잡는 것에서 시작한다. 다음 절에서는 이 두 신호와 hysteresis · cooldown 을 합쳐 실제로 작동하는 정책을 C 로 직접 구현한다.
