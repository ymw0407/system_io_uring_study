## 이번 실습의 목표

1회차에서 io_uring의 동작을 C 코드로 직접 체험했다. `clock_gettime`으로 대략적인 지연을 찍어 보았지만, 측정 harness 자체가 오버헤드를 만들 수 있고 워밍업이나 정상 상태(steady-state) 판정도 없었다. 이번에는 실험이다. QD를 바꾸고, 모드를 바꾸고, CPU 부하를 바꾸면서 성능이 어떻게 달라지는지 정밀하게 측정한다. 이 매트릭스를 C로 짜면 수백 줄이고, 한 줄 실수하면 전부 다시 돌려야 한다. fio를 쓰면 셸 스크립트 한 장이면 된다.

## 왜 fio인가

fio(Flexible I/O Tester)는 리눅스 블록 I/O 벤치마크의 사실상 표준 도구다. `--ioengine=io_uring`을 지정하면 내부적으로 liburing을 사용하여 io_uring 경로를 정확히 행사하며, SQPOLL과 IOPOLL 같은 세부 모드까지 플래그 하나로 제어할 수 있다. fio는 워밍업, 정상 상태 감지, 백분위 지연 계산, JSON 출력을 자체적으로 처리하므로, C로 직접 구현해야 할 측정 인프라를 통째로 대체한다.

## fio 설치 및 기본 사용법

<Steps>
  <Step title="fio 설치">

대부분의 배포판에서 패키지 매니저로 설치할 수 있다. io_uring 엔진은 fio 3.13 이상에서 지원된다.

<Terminal title="fio 설치 및 버전 확인" commands={[
  { cmd: "sudo apt install fio", output: ["Reading package lists...", "Setting up fio (3.36-1) ..."] },
  { cmd: "fio --version", output: ["fio-3.36"] },
  { cmd: "fio --enghelp | grep io_uring", output: ["io_uring"] }
]} />

`fio --enghelp`에서 `io_uring`이 보이면 엔진이 활성화된 빌드다.

  </Step>
  <Step title="첫 번째 fio 실행">

가장 기본적인 io_uring 랜덤 읽기 명령을 실행한다.

<Terminal title="기본 fio 실행" commands={[
  { cmd: "fio --name=basic --ioengine=io_uring --rw=randread --bs=4k --direct=1 --iodepth=16 --filename=/dev/nvme0n1 --runtime=10 --time_based --size=1G", output: ["basic: (groupid=0, jobs=1): err= 0: pid=12345", "  read: IOPS=34.2k, BW=133MiB/s (140MB/s)", "    slat (nsec): min=1200, max=52000, avg=2100", "    clat (usec): min=35, max=890, avg=118.2", "     lat (usec): min=37, max=892, avg=120.3"] }
]} />

`--ioengine=io_uring`은 io_uring 백엔드를 선택한다. `--rw=randread`는 4KB 랜덤 읽기, `--direct=1`은 페이지 캐시를 우회하여 디바이스 지연을 직접 측정한다. `--iodepth=16`은 동시에 16개의 요청을 in-flight 상태로 유지한다. `--time_based`는 지정된 `--runtime` 동안 반복 실행하라는 뜻이다.

출력에서 `clat`(completion latency)의 `avg`가 핵심 지표다. 이 값이 NVMe 4KB random read의 전형적인 범위인 80~120 마이크로초 안에 있으면 정상이다.

  </Step>
</Steps>

<Callout kind="tip">
`--direct=1`은 `O_DIRECT` 플래그를 켜서 페이지 캐시를 우회한다. 이 옵션을 빼면 운영체제 캐시에서 데이터를 읽는 비율이 높아져, 디바이스 I/O가 아닌 메모리 접근 속도를 측정하게 된다. 블록 디바이스 성능을 측정할 때는 반드시 켜야 한다.
</Callout>

## 모드별 fio 옵션

io_uring에는 세 가지 주요 동작 모드가 있다. fio에서 각각을 어떻게 활성화하는지 정리한다.

<Steps>
  <Step title="Interrupt 모드 (기본)">

추가 플래그 없이 `--ioengine=io_uring`만 지정하면 기본 모드, 즉 interrupt 방식으로 동작한다. 애플리케이션이 `io_uring_enter` 시스템 콜로 요청을 제출하고, 완료 시 커널이 인터럽트를 통해 CQE를 채운다.

<Terminal title="Interrupt 모드" commands={[
  { cmd: "fio --name=int --ioengine=io_uring --rw=randread --bs=4k --direct=1 --iodepth=16 --filename=/dev/nvme0n1 --runtime=30 --time_based --output-format=json --output=results/default-qd16.json" }
]} />

  </Step>
  <Step title="SQPOLL 모드">

`--sqthread_poll=1`을 추가하면 fio 내부에서 `IORING_SETUP_SQPOLL` 플래그를 설정한다. 커널이 전용 kthread를 생성하여 SQ를 지속적으로 감시하므로, 제출 경로의 시스템 콜이 제거된다.

<Terminal title="SQPOLL 모드" commands={[
  { cmd: "sudo fio --name=sqpoll --ioengine=io_uring --sqthread_poll=1 --rw=randread --bs=4k --direct=1 --iodepth=16 --filename=/dev/nvme0n1 --runtime=30 --time_based --output-format=json --output=results/sqpoll-qd16.json" }
]} />

SQPOLL은 커널 5.12 이전에서는 `CAP_SYS_ADMIN`이 필요하다. 권한 오류가 발생하면 `sudo`로 실행한다.

  </Step>
  <Step title="IOPOLL 모드">

`--hipri=1`을 추가하면 `IORING_SETUP_IOPOLL` 플래그가 설정된다. 이 모드는 완료 경로를 폴링으로 전환하여, 커널이 디바이스 completion queue를 직접 확인한다. NVMe처럼 polling-capable 디바이스에서만 동작하며, `O_DIRECT`가 필수다.

<Terminal title="IOPOLL 모드" commands={[
  { cmd: "sudo fio --name=iopoll --ioengine=io_uring --hipri=1 --rw=randread --bs=4k --direct=1 --iodepth=16 --filename=/dev/nvme0n1 --runtime=30 --time_based --output-format=json --output=results/iopoll-qd16.json" }
]} />

SQPOLL이 제출 경로의 시스템 콜을 제거한다면, IOPOLL은 완료 경로의 인터럽트를 제거한다. 둘은 독립적인 최적화이며 동시에 사용할 수도 있다.

  </Step>
</Steps>

<Callout kind="note">
SQPOLL과 IOPOLL을 혼동하기 쉽다. SQPOLL은 커널 스레드가 SQ(Submission Queue)를 감시하여 제출 시스템 콜을 없앤다. IOPOLL은 디바이스 레벨에서 completion을 폴링하여 완료 인터럽트를 없앤다. 제거하는 대상이 다르다.
</Callout>

## 실험 매트릭스 스크립트

세 모드와 다섯 단계의 QD를 조합하면 총 15회의 실험이 필요하다. 이를 셸 스크립트 하나로 자동화한다.

<CodeBlock language="bash" filename="run_matrix.sh">
{`#!/bin/bash
# run_matrix.sh — mode x QD experiment matrix
# usage: sudo ./run_matrix.sh

MODES=("default" "sqpoll" "iopoll")
QDS=(1 4 16 64 256)
DEVICE="/dev/nvme0n1"
RUNTIME=30
OUTDIR="results"

mkdir -p "$OUTDIR"

for mode in "\${MODES[@]}"; do
  EXTRA=""
  if [ "$mode" = "sqpoll" ]; then
    EXTRA="--sqthread_poll=1"
  fi
  if [ "$mode" = "iopoll" ]; then
    EXTRA="--hipri=1"
  fi

  for qd in "\${QDS[@]}"; do
    echo ">>> Running: mode=$mode qd=$qd"
    fio --name="\${mode}-qd\${qd}" \\
        --ioengine=io_uring \\
        --rw=randread --bs=4k --direct=1 \\
        --iodepth="$qd" \\
        --filename="$DEVICE" \\
        --runtime="$RUNTIME" --time_based \\
        --output-format=json \\
        $EXTRA \\
        --output="\${OUTDIR}/\${mode}-qd\${qd}.json"
  done
done

echo "Done. Results in $OUTDIR/"
ls -1 "$OUTDIR"/*.json | wc -l
echo "JSON files generated."`}
</CodeBlock>

<Terminal title="실험 매트릭스 실행" commands={[
  { cmd: "chmod +x run_matrix.sh && sudo ./run_matrix.sh", output: [">>> Running: mode=default qd=1", ">>> Running: mode=default qd=4", "...", ">>> Running: mode=iopoll qd=256", "Done. Results in results/", "15", "JSON files generated."] }
]} />

전체 실행에는 약 7분 30초(15회 x 30초)가 소요된다. 각 실험의 결과는 `results/` 디렉터리에 JSON 파일로 저장된다.

## JSON 결과 파싱

fio의 JSON 출력에서 핵심 지표를 추출한다. `jq`를 사용하면 한 줄로 원하는 필드를 뽑을 수 있다.

<Terminal title="단일 파일에서 지표 추출" commands={[
  { cmd: "jq '.jobs[0].read.lat_ns.mean / 1000' results/default-qd16.json", output: ["118.234"] },
  { cmd: "jq '.jobs[0].read.iops' results/default-qd16.json", output: ["34215.8"] },
  { cmd: "jq '{usr: .jobs[0].usr_cpu, sys: .jobs[0].sys_cpu}' results/sqpoll-qd16.json", output: ["{", "  \"usr\": 3.2,", "  \"sys\": 95.1", "}"] }
]} />

15개 파일을 하나씩 열기보다는 파싱 스크립트로 CSV를 한번에 뽑는 편이 낫다.

<CodeBlock language="bash" filename="parse_results.sh">
{`#!/bin/bash
# parse_results.sh — extract key metrics from fio JSON
# output: CSV to stdout

OUTDIR="results"

echo "mode,qd,lat_us,iops,bw_MBs,usr_cpu,sys_cpu"

for f in "$OUTDIR"/*.json; do
  base=$(basename "$f" .json)
  mode=$(echo "$base" | cut -d'-' -f1)
  qd=$(echo "$base" | sed 's/.*qd//')

  lat=$(jq '.jobs[0].read.lat_ns.mean / 1000' "$f")
  iops=$(jq '.jobs[0].read.iops' "$f")
  bw=$(jq '.jobs[0].read.bw_bytes / 1048576' "$f")
  usr=$(jq '.jobs[0].usr_cpu' "$f")
  sys=$(jq '.jobs[0].sys_cpu' "$f")

  printf "%s,%s,%.1f,%.0f,%.1f,%.1f,%.1f\\n" \\
    "$mode" "$qd" "$lat" "$iops" "$bw" "$usr" "$sys"
done | sort -t, -k1,1 -k2,2n`}
</CodeBlock>

## QD별 지연 비교

세 모드의 QD별 평균 지연을 하나의 그래프로 겹쳐 본다.

<Chart
  kind="line"
  data={fioQdLatency}
  xKey="qd"
  yScale="log"
  series={[
    { key: 'interrupt', label: 'Interrupt', color: 'interrupt' },
    { key: 'sqpoll', label: 'SQPOLL', color: 'polling' },
    { key: 'iopoll', label: 'IOPOLL', color: 'adaptive' },
  ]}
  xLabel="Queue Depth"
  yLabel="Latency (us, log scale)"
  caption="QD별 평균 지연 (베어메탈 Arch Linux, WD Black SN950X NVMe, 8-core, idle, nvme.poll_queues=4). Y축은 log 스케일이라 저 QD 의 mode 간 차이가 시각적으로 보임."
/>

곡선의 모양이 QD에 따라 셋으로 갈린다.

**저 QD (1~4) — polling이 본래 약속한 효과가 보인다.** QD=1에서 interrupt 48μs, SQPOLL 42μs, IOPOLL 41μs로 polling 두 모드가 약 13% 빠르다. 이 격차는 정확히 syscall 한 번(~0.3μs)과 IRQ 핸들링·컨텍스트 스위치(~1~3μs)를 합한 비용에 해당한다. polling이 줄여 줄 비용은 본래 이 정도이고, 책에서 인용되는 더 큰 수치는 Optane처럼 디바이스 지연 자체가 ≤10μs 인 경우의 비례 효과다.

**중 QD (4~64) — IOPOLL이 오히려 느려진다.** QD=16에서 IOPOLL 66μs로 interrupt 46μs 대비 43% 더 느리다. 이유는 IOPOLL이 사용자 공간에서 `io_uring_enter()` 안에 머물며 NVMe completion을 spin-poll 하기 때문이다. polling 시간이 늘어나면 같은 스레드가 새 SQE를 제출할 여유가 줄어, 디바이스에 깔리는 동시 요청 수가 의도한 QD에 못 미친다. SQPOLL은 제출 쪽을 별도 커널 스레드에 분리해 두어 이 함정에서 자유롭다. 결과적으로 SQPOLL은 interrupt와 거의 동일한 지연을 유지한다.

**고 QD (256) — 세 모드가 다시 수렴한다.** interrupt 476μs, SQPOLL 480μs, IOPOLL 477μs. 디바이스가 포화 상태에 들어가 새 요청이 큐에서 대기하기 시작하면, Little's Law 에 의해 평균 지연 ≈ QD / 처리율 이 되어 모드별 마이크로초 단위 차이는 ms 단위 큐잉 지연에 묻힌다.

요약하면 polling이 의미를 갖는 구간은 *디바이스가 빠르고 QD가 낮은 좁은 영역*뿐이다. 그 바깥에서는 syscall/IRQ 비용이 디바이스 지연 또는 큐잉 지연 안에 흡수된다.

## CPU 사용량 비교

모드별로 fio가 보고하는 CPU 사용률을 확인한다. QD=16, 동일 런타임 조건에서 측정한 값이다.

/>

지연은 모드 간 차이가 작았는데 CPU 프로파일은 극명하게 갈린다.

- **Interrupt** — usr 6%, sys 19%, 합 25%. 프로세스가 대부분 sleep 상태이며 syscall 진입과 인터럽트 핸들링이 시스템 시간으로 잡힌다.
- **SQPOLL** — usr 100%, sys 0%. 메인 fio 프로세스는 SQ에 SQE를 쓰고 CQ를 user-space에서 폴링만 하므로 syscall이 사실상 사라진다. 단, 이 수치는 fio 프로세스 한정 통계다. **별도 커널 스레드(`io_uring-sq`)가 다른 코어를 100% 점유하는 비용은 여기 포함되지 않는다**. 시스템 전체로 보면 SQPOLL은 코어 두 개를 상시 점유한다.
- **IOPOLL** — usr 4%, sys 95%. fio가 `io_uring_enter()` 안에서 NVMe completion을 spin-poll하므로 폴링 시간이 전부 시스템 시간으로 잡힌다.

이 그림이 polling의 본질을 보여 준다 — polling은 work의 *총량*을 줄이지 않고 *어디서, 언제* 일하는지를 재배치한다. 같은 양의 CPU 시간을 쓰면서도 IRQ 경로의 latency를 제거함으로써 *지연*만 짧아진다.

이 trade-off의 진짜 비용은 시스템에 다른 부하가 끼어들 때 드러난다. 다음 절에서 본다.

## CPU 부하 실험

SQPOLL이 CPU 코어 하나를 상시 점유한다면, 다른 작업이 CPU를 두고 경쟁할 때 어떤 일이 벌어지는가. `stress-ng`로 CPU 부하를 단계별로 올리면서 처리량 변화를 측정한다.

<Steps>
  <Step title="부하 없이 측정 (Idle)">

다른 부하 없이 fio만 실행한다. QD=16을 기준으로 interrupt와 SQPOLL의 처리량을 각각 기록한다.

<Terminal title="Idle 상태 측정" commands={[
  { cmd: "fio --name=idle-int --ioengine=io_uring --rw=randread --bs=4k --direct=1 --iodepth=16 --filename=/dev/nvme0n1 --runtime=30 --time_based --output-format=json --output=results/cpu-idle-int.json" },
  { cmd: "sudo fio --name=idle-sqp --ioengine=io_uring --sqthread_poll=1 --rw=randread --bs=4k --direct=1 --iodepth=16 --filename=/dev/nvme0n1 --runtime=30 --time_based --output-format=json --output=results/cpu-idle-sqp.json" }
]} />

  </Step>
  <Step title="CPU 50% 부하">

`stress-ng`로 코어 절반에 연산 부하를 건다. 아래 예시는 8코어 시스템 기준이며, 코어 수에 맞게 조정한다.

<Terminal title="CPU 50% 부하 + fio 측정" commands={[
  { cmd: "stress-ng --cpu 4 --timeout 60s &", output: ["[1] 12345"] },
  { cmd: "fio --name=cpu50-int --ioengine=io_uring --rw=randread --bs=4k --direct=1 --iodepth=16 --filename=/dev/nvme0n1 --runtime=30 --time_based --output-format=json --output=results/cpu50-int.json" },
  { cmd: "sudo fio --name=cpu50-sqp --ioengine=io_uring --sqthread_poll=1 --rw=randread --bs=4k --direct=1 --iodepth=16 --filename=/dev/nvme0n1 --runtime=30 --time_based --output-format=json --output=results/cpu50-sqp.json" }
]} />

  </Step>
  <Step title="CPU 100% 부하">

모든 코어를 포화시킨다. `$(nproc)`은 시스템의 전체 코어 수로 치환된다.

<Terminal title="CPU 100% 부하 + fio 측정" commands={[
  { cmd: "stress-ng --cpu $(nproc) --timeout 60s &", output: ["[1] 12350"] },
  { cmd: "sudo fio --name=cpu100-int --ioengine=io_uring --rw=randread --bs=4k --direct=1 --iodepth=16 --filename=/dev/nvme0n1 --runtime=30 --time_based --output-format=json --output=results/cpu100-int.json" },
  { cmd: "sudo fio --name=cpu100-sqp --ioengine=io_uring --sqthread_poll=1 --rw=randread --bs=4k --direct=1 --iodepth=16 --filename=/dev/nvme0n1 --runtime=30 --time_based --output-format=json --output=results/cpu100-sqp.json" }
]} />

  </Step>
</Steps>

Idle과 50% 부하에서는 두 모드의 처리량이 거의 같다 — 약 1.3 GB/s. 베어메탈 NVMe + QD=16 환경에서 폴링이 throughput에 주는 추가 이점은 1% 안쪽이라는 뜻이다. (앞 절에서 본 *지연* 차이도 비슷한 크기였다.)

판세는 **CPU 100% 부하에서** 갈린다. interrupt는 1025 MB/s 로 idle 대비 76% 를 유지하지만, SQPOLL은 564 MB/s 로 idle의 42% 까지 떨어진다. 절대값으로 1345 → 564 — 처리량이 절반 이하가 됐다.

이유는 SQPOLL의 *작동 전제*가 무너졌기 때문이다. SQPOLL은 별도 커널 스레드(`io_uring-sq`)가 SQ를 *지속적으로* 폴링한다는 가정 위에 서 있는데, 모든 코어가 stress-ng 로 포화되면 이 스레드도 다른 워크로드와 경쟁해 시간 분할을 받게 된다. 폴링이 끊기면 fio 가 SQ에 SQE를 깔아도 즉시 디바이스로 내려가지 못해 제출 지연이 누적되고, 동시에 한 번 폴링 사이클이 돌 때 처리할 수 있는 IO 수도 줄어든다. *제거하려고 했던 syscall 비용을 능가하는 스케줄링 비용*이 새로 붙는 것이다.

interrupt 모드는 IRQ 가 들어오는 순간에만 짧게 핸들러를 돌리고 끝나므로 코어 점유 시간이 본래 작다. 따라서 다른 워크로드와 경쟁해도 기여 시간 비율 자체가 작고, throughput 감소가 비례적으로 작다.

<Callout kind="checkpoint">
이것이 Part 4에서 adaptive 가 필요한 이유다. CPU 가 한가할 때는 polling 이 약간이나마 더 효율적이지만 (특히 *지연* 측면, 이 실험에서 보인 throughput 차이는 작음), 부하가 차면 polling 의 가정이 깨져 오히려 큰 손해를 본다. 어떤 단일 모드도 전 구간에서 최적이 아니다.
</Callout>

### 두 환경을 나란히 보면

| 지표 | 베어메탈 (Arch + SN950X) | 가상화 (QEMU on macOS) |
|---|---|---|
| 디바이스 평균 latency @ QD=1 | ~48 μs | ~36 μs (※emulation 자체가 빠른 path 흉내) |
| 디바이스 평균 latency @ QD=16 | ~46 μs | ~135 μs (queueing 비용 폭발) |
| polling 이 latency 에 도움되는 영역 | QD 1 ~ 4 (~13%) | QD 16 ~ 64 (~5%) |
| polling 의 sweet spot | 저 QD | 중간 QD |
| CPU 비용 패턴 | 동일 (polling 100%) | 동일 |

*같은 정책이 환경에 따라 다른 곳에서 의미를 갖는다.* 베어메탈에서는 빠른 디바이스 덕에 OS path 가 latency 의 ~10% 이상이라 저 QD 에서도 polling 이 깎을 양이 있다. QEMU 환경에서는 virtualization 비용이 latency 를 키워 OS path 비율이 ~2% 로 줄고, polling 의 의미 있는 영역이 중간 QD 로 이동한다.

### QEMU 환경에서 polling 차이가 사라지는 *구조적* 이유

이 차이는 단순히 "QEMU 가 더 느려서" 가 아니다. *가상화 layer 가 OS path 를 두 단계로 늘리는데, 그 두 번째 단계는 guest 의 polling 으로 접근할 수 없기* 때문이다. IO 한 건이 거치는 경로를 보면 명확해진다.

<CodeBlock language="plaintext" filename="qemu-io-path.txt">
{`[Guest]    fio → io_uring_enter (guest 커널)
              ↓
[KVM]      hypercall → 호스트 커널 진입
              ↓
[Host]     호스트 storage stack → 호스트 driver → 실제 디바이스
                                                       ↓
[Host]     실제 디바이스 IRQ → 호스트 → KVM
              ↓
[Guest]    가상 IRQ → 게스트 커널 → fio`}
</CodeBlock>

베어메탈에서 OS path 였던 부분이 *guest OS path + host OS path* 로 둘로 쪼개진다. SQPOLL · IOPOLL 같은 guest 측 polling 옵션이 깎을 수 있는 건 *guest 측 작은 부분*뿐이고, 호스트 storage stack + KVM 비용은 그대로 남는다.

게다가 IOPOLL 의 핵심 메커니즘은 *NVMe 컨트롤러의 poll queue* 에서 결과를 가져오는 것이다. 가상 NVMe (virtio-blk passthrough 포함) 는 이 poll queue 를 흉내내지 못한다 — 호스트가 결국 인터럽트로 처리한 다음 guest 에 전달한다. 즉 IOPOLL 의 "인터럽트 회피" 라는 본질이 가상 환경에서는 *동작하지 않는다*.

결과적으로 측정 결과를 정리하면:

| 비용 영역 | 베어메탈 | QEMU |
|---|---|---|
| Guest 측 syscall + IRQ | 폐 polling 으로 회피 가능 | polling 으로 회피 가능 |
| Host 측 storage stack + KVM | 해당 없음 | **polling 으로 회피 불가** |
| 디바이스 자체 시간 | 핵심 비용 | 같음 (passthrough 시) |

폐기 가능한 부분이 latency 의 작은 비율로 줄어들고, 그 작은 부분조차 IOPOLL 의 메커니즘이 동작 안 하므로, *모드 간 측정 차이는 noise 수준으로 묻힌다*.

<Callout kind="warn">
이 study 의 학습자가 자기 개발 머신 (대부분 macOS / Windows + VM 또는 클라우드 VM) 에서 io_uring 을 측정하면, 문헌이나 베어메탈 결과의 "polling 13% 빠름" 같은 그림이 *안 나오는 게 정상*이다. 정책 코드의 버그가 아니고, polling 이 실패한 것도 아니다 — *polling 이 깎으려 한 비용이 측정 환경에 존재하지 않을 뿐*이다.

io_uring 의 모드별 효과를 진짜로 보려면 베어메탈 + NVMe + poll_queues 설정이 모두 필요하다. 그 외 환경에서는 모드 선택이 측정 noise 안에 묻힌다.
</Callout>

## 핵심 관찰

두 환경의 측정에서 일관되게 확인된 것은 다음 여섯이다.

1. **polling 의 의미 있는 영역은 *좁고*, 그 영역의 위치는 *환경에 따라 다르다*** — 빠른 디바이스에서는 저 QD, 느린/가상화 환경에서는 중간 QD.
2. **polling 의 latency 이득은 모든 환경에서 작다** — 베어메탈 sweet spot 에서 ~13%, QEMU sweet spot 에서 ~5%. 책에서 인용되는 더 큰 수치는 더 빠른 디바이스 (Optane 등) 의 비례 효과.
3. **CPU 비용은 환경 무관하게 항상 3~7 배 비싸다** — polling 두 모드는 디바이스가 무엇이든 100% 코어를 점유한다.
4. **고 QD 에서는 모든 환경에서 세 모드가 수렴** — 디바이스 내부 큐가 saturated 되면 OS 모드 선택은 의미가 없다.
5. **CPU 부하가 차면 SQPOLL 처리량이 절반 이하로 무너진다** — interrupt 76% 유지, SQPOLL 42% 까지 (베어메탈 stress-ng 실험).
6. **가상화 환경에서는 모드 선택의 효과가 구조적으로 사라진다** — guest 측 polling 이 깎을 수 있는 비용은 latency 의 일부에 불과하고, host storage stack + KVM 비용이 그대로 남는다. IOPOLL 의 NVMe poll queue 메커니즘은 가상 NVMe 에서 동작하지 않는다. *VM 위 측정으로 io_uring 의 모드 효과를 판단하지 말 것*.

같은 결론을 가리킨다. *polling 은 work 의 총량을 줄이지 않고 위치를 바꿀 뿐이며, 그 재배치가 효율적인지 여부는 시스템 전체 상황 (디바이스 속도, 가상화 layer, QD, CPU 경합) 에 의존한다*. "항상 polling" 도 "항상 interrupt" 도 정답이 아니다. Part 4 에서는 위 축들을 런타임에 관찰해 모드를 동적으로 전환하는 adaptive 정책을 살펴본다.

<Callout kind="warn">
fio와 직접 작성한 C 벤치마크의 결과를 나란히 비교할 때는 주의가 필요하다. fio는 내부적으로 워밍업, 스레드 관리, 통계 수집 등의 인프라가 동작하므로, 동일한 io_uring 모드를 사용하더라도 C 코드의 결과와 미묘하게 다를 수 있다. 3회차에서 adaptive C 벤치마크와 fio 결과를 비교할 때 이 한계를 명시해야 한다.
</Callout>
